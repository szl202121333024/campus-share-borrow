# 人类评审手册（Review Playbook）

> 用途：你是这个项目的**产品负责人兼架构评审人**。AI 产出草稿后，你对照本手册挑毛病、照抄台词驳回。
> 这不是"找茬"，是把评审标准前置成清单——老师看的是你有没有真实判断，不是你有没有全盘接受。

## 0. 三条铁律

1. **每条否决必须指向依据**：FR / NFR / ADR 编号，或"工期/运维能力"这类真实约束。说不出依据的否决，记为无效。
2. **否决必须给替代方案**：只说"不行"是耍脾气，"不行，改成 X，因为 Y"才是决策。
3. **质量 > 数量**：够了 5 条实质否决就收手。硬凑 15 条会把日志写成流水账，反而扣分。

**通用三句式**（任何场景都能套）：

> ① 指出问题：「这里只写了 ___，没写 ___，不可验收。」
> ② 给替代：「改成 ___，因为 ___（指向 FR/NFR/ADR）。」
> ③ 要求留痕：「按这个改，然后记为 ADR-00X / decision-log 第 N 条。」

## 阶段 1：PRD（`bmad-prd`）

AI 写 PRD 时最容易犯的四个毛病，逐条对应一句台词。

### 驳点 1-1：限额规则没有数字

**破绽**：FR-5 只写"用户有借阅限额"，没写上限是多少、超限返回什么。

> 停。FR-5 只写了"有借阅限额"，没写数值也没写超限行为，这条没法验收。
> 改成：**每个用户同时最多借 3 件**；已达上限时借阅请求返回 **409**，错误码 `LIMIT_EXCEEDED`，页面提示"你已借满 3 件，请先归还"。
> 理由：NFR-2 要求可运维、可测试，模糊需求等于没需求。改完记 decision-log。

### 驳点 1-2：NFR-1 不可测

**破绽**：NFR-1 写成"保证并发一致性"这类口号。

> NFR-1 现在是口号，不是验收标准。改成可执行的：
> **同一物品被两个并发请求借阅时，恰好一个成功（HTTP 200），另一个失败（HTTP 409），数据库中该物品的借阅记录恰好 1 条，物品状态不发生二次变更。**
> 这是全项目唯一的技术难点，标准必须硬到能写测试。改完记 decision-log。

### 驳点 1-3：归还期限缺失

**破绽**：FR-4 归还只写"可以归还"，没有期限、没有逾期概念。

> FR-4 没定义借期。补上：**借期 7 天**，逾期不影响归还操作，但列表页标红提示"已逾期 N 天"。本期**不做**逾期罚款、不做自动催还——写进"明确不做"。

### 驳点 1-4：管理员权限边界模糊

**破绽**：FR-6 写"管理员可以增删"，没说删的时候有在借记录怎么办。

> FR-6 有漏洞：管理员删除一件**正在被借阅**的物品会怎样？规定：**存在未归还记录时禁止删除，返回 409 并提示"该物品在借中，无法删除"**。这条要有验收标准。

**阶段 1 收尾动作**：确认 PRD 里 `FR-1 ~ FR-6`、`NFR-1`、`NFR-2`、"明确不做"三样齐全，然后 `git commit -m "docs: add PRD"`。

## 阶段 2：架构（`bmad-architecture`）—— 剧本核心，两发重炮

这一阶段 AI 会**故意**先提两个烂方案。别犹豫，按下面原话打回去。

### 驳点 2-1：React 方案 → ADR-001

**AI 会说**：为了"现代感"，建议 React 前端 + RESTful API。

> **我否决 React 方案。**
> 理由两条：① 作业约束和技术栈限制明确禁止前后端分离；② NFR-2 要求"一条命令启动"，我不懂运维，多一条前端构建链就多一个故障点，工期也不允许。
> **改用 Flask + Jinja2 服务端直接渲染。** 记 **ADR-001**：决定 = 服务端渲染；否决的备选 = React SPA + REST API；理由 = 运维复杂度与工期。

### 驳点 2-2：先查后写 → ADR-002

**AI 会说**：借阅逻辑先 `SELECT` 查库存，可借再 `UPDATE`。

> **我否决"先查后写"。**
> 两个人同时查，都会看到"可借"，然后都执行 UPDATE，结果两个人都借成功——这就是超卖，直接违反 NFR-1。
> **必须用数据库唯一索引兜底**：在借阅表上建**部分唯一索引** `CREATE UNIQUE INDEX ux_loans_active_item ON loans(item_id) WHERE returned_at IS NULL` —— 列是 **`item_id` 单列**（不是 `(user_id, item_id)`），条件只作用于未归还记录，让**数据库**拒绝第二个写入；代码捕获 `IntegrityError` 后返回 409「该物品已被借走」。
>
> > 📌 **原手册错误，经架构阶段验证修正（D-018）**：初版写的是 `UNIQUE(user_id, item_id)`，两处错——① 它只约束「同一人不能重复持有同一物品」，**两个不同用户仍可同时借走同一件**，防不住超卖，直接违反 NFR-1.1；② 不带 `WHERE` 会让已归还的历史记录永久占用组合键，导致归还后再也借不了同一件，违反 FR-3。修正后为 `item_id` 上的部分唯一索引。详见 `_bmad-output/planning-artifacts/architecture/adr-campus-share-borrow-2026-11-08/ADR-002-concurrency-uniqueness.md`。
> 记 **ADR-002**：决定 = 唯一索引兜底（防物品超卖）+ `BEGIN IMMEDIATE` 写事务（防额度并发越限）+ 捕获 `IntegrityError` 返回 409；否决的备选 = 仅靠应用层 `SELECT` 检查、或单纯用写锁代替唯一索引来充当唯一性裁决者；理由 = 唯一索引是物理底线的最后一道闸，写事务是业务校验的原子保证，两者分工明确、缺一不可。

### 驳点 2-3 ~ 2-5：另外三条 ADR 的候选靶子

凑满 5 条 ADR 用。看到 AI 这么写，就这么驳：

| AI 可能建议 | 你的台词 | ADR |
|---|---|---|
| 用 JWT 存 token | 「单人课程项目，JWT 要处理刷新、过期、吊销，成本远超收益。改用 Flask session + 服务端 cookie，登出即失效。」 | ADR-003：会话方案 |
| 密码明文或 MD5 存库 | 「密码必须 `werkzeug.security.generate_password_hash`（PBKDF2），不可逆。这条不是可选项。」 | ADR-004：密码存储 |
| 直接多进程部署 / gunicorn 多 worker | 「SQLite 在多写并发下会 `database is locked`。开启 **WAL 模式** + `busy_timeout`，部署单进程即可，NFR-2 只要一条命令。」 | ADR-005：并发与部署 |

**阶段 2 收尾动作**：数一遍——**5 条 ADR，每条都有"决定 / 否决的备选 / 理由"**，缺一条就打回。然后 `git commit -m "docs: add architecture and ADRs"`。

## 阶段 3：史诗与故事（`bmad-create-epics-and-stories`）

### 驳点 3-1：故事超出 PRD 范围

**破绽**：AI 自发加了"评论""通知""图片上传"这类 PRD 里"明确不做"的东西。

> 停。故事 X.X 超出 PRD 范围——PRD 的"明确不做"里写了评论/图片上传/跨班共享。**删掉，不要放进本迭代**。
> 理由：范围蔓延会让 12 个故事的工期失控。这条记 decision-log（这也是作业要求的第 3 个决策点）。

### 驳点 3-2：验收标准不可测

**破绽**：故事验收写成"用户可以顺利借阅"。

> 这不是验收标准，是愿望。改成 Given/When/Then：
> **Given 物品 A 可借、用户 U 未借满 3 件；When U 提交借阅；Then 返回 200，物品 A 状态变为"借出中"，借阅记录新增 1 条且 borrower=U。**

### 驳点 3-3：并发故事被漏掉

**破绽**：12 个故事里没有一个专门覆盖 NFR-1。

> 12 个故事全在讲正常流程，**没有一条覆盖 NFR-1**。补一个故事：「并发借阅冲突处理」，验收标准就是阶段 1 那条 NFR-1 的原文。
> 这条是整个作业的技术命门，不能只活在 NFR 里。

**阶段 3 收尾动作**：确认 3 史诗 / ≥12 故事 / 每条验收可测 / `project-context.md` ≥8 条规则。然后 `git commit -m "docs: add epics, stories and project context"`。

## 阶段 4：实施（`bmad-sprint-planning` → `bmad-build`）

### 驳点 4-1：测试没有并发场景

**破绽**：AI 说"测试通过"，但只测了单人借阅。

> 你的测试只覆盖单人借阅，**证明不了 NFR-1**。补一个并发测试：用 `threading` 起两个线程同时 POST 同一个物品的借阅请求，断言**恰好 1 个 200、1 个 409**，且数据库里借阅记录只有 1 条。
> 这就是作业要求的第 4 个决策点：测试中发现并发漏洞并修正。

### 驳点 4-2：没按 project-context.md 的规约写

**破绽**：命名风格、目录结构跟 `project-context.md` 不一致。

> 你写的 `borrowBook()` 用的是驼峰，`project-context.md` 第 3 条规约是 snake_case。**按规约改**。
> 理由：实验 A 对照组要证明的正是"没有项目规约会导致代码风格漂移"——实验组自己先漂了，实验就没意义了。

## 阶段 5：实验 A

### 对照组怎么问（关键：一个字都不能多说）

新开一个**干净对话**，只说这一句：

> 帮我写一个添加物品的功能。

**不给技术栈、不给字段、不给命名规范、不给错误处理要求。** 它写成什么样就是什么样。

### 评审对照组的话术

> 按实验组的同一套标准评审：① 字段命名是否符合 snake_case ② 是否有输入校验 ③ 是否有权限检查 ④ 是否有测试。
> 不合格就如实写不合格——**给对照组放水，整个实验结论就废了**。

### 回顾结论（照实写，别美化）

- 极简功能（添加物品）：完整规划的阅读成本 > 收益，**收益为负**。
- 核心并发逻辑（借阅/归还）：架构前置直接避免了返工，**收益为正**。
- 两条都要写进 `retrospective.md`，负面结论反而加分。

## 附：decision-log 草稿模板

每次我提示"发现决策点"时，你在 `decision-log.md` 里按下表填一行：

| # | 触发 | 智能体建议 | 人类判断依据 | 结果 | 事后验证 |
|---|---|---|---|---|---|
| 1 | 架构选型 | React + REST API | NFR-2（一条命令启动）、工期、技术栈限制 | 改为 Flask + Jinja2 SSR，记 ADR-001 | 阶段 4 启动耗时 < 10s |
| 2 | 借阅并发 | SELECT 查库存再 UPDATE | NFR-1（并发一致性） | 改唯一索引兜底 + 捕获 IntegrityError，记 ADR-002 | 并发测试 1 成功 1 冲突 |

**"事后验证"这一列最容易漏，也最能说明你不是拍脑袋否决**——所以每次否决完，记住它后来被什么证据印证了。
