# ADR-003 · 会话方案：Flask 签名 cookie session（无状态）

**决定：使用 Flask 内置的签名 cookie session，会话数据存于客户端 cookie（itsdangerous 签名），服务端不存储会话。**

**否决的备选：JWT（Bearer token）；Flask-Session（服务端会话存储，含 Redis / 文件系统后端）；自建 `sessions` 表。**

## 1. 背景

FR-1 对会话提出四条可测要求：① 登录成功下发凭据，随后 `GET /my-loans` 返回 200；② 登出后该会话凭据失效；③ 闲置超过 24 小时失效；④ 未登录访问受保护页面 → 302 到 `/login?next=`。

技术前提已被 ADR-001 固定：同源、单进程、服务端渲染，浏览器与服务器之间只有 cookie 一条通道，不存在跨域 API 调用。规模上：单班、种子 2 个学生 + 1 个管理员账号（PRD NFR-2、A-4），无横向扩容需求。NFR-2 要求「单文件库 + 无外部服务依赖」，这直接排除了 Redis。

**必须先承认一个底层限制**：无状态签名 cookie 的「失效」只能由**客户端删除**达成；服务端无法让一张已经签发出去的 cookie 提前作废（除非引入服务端状态）。FR-1 的验收语句「用旧 cookie 访问 `GET /my-loans` → 302」在浏览器行为层面成立（cookie 已被清除），但在「攻击者持有 cookie 副本」的层面**做不到**。这是本 ADR 的核心取舍，已由人类裁决接受（D-019）。

## 2. 决定

- **机制**：Flask 内置 `session`（客户端签名 cookie，`itsdangerous` HMAC 签名，**签名不等于加密**——内容可被读取，不可被篡改）。
- **会话内容**：只放 `user_id`、`role`、`login_at` 三个短字段。**不放密码、哈希、学号全量信息、任何业务数据**。cookie 上限 4KB，此设计远低于上限。
- **闲置 24 小时失效**：`session.permanent = True` + `PERMANENT_SESSION_LIFETIME = 24h` + `SESSION_REFRESH_EACH_REQUEST = True`（Flask 默认），即每次请求刷新到期时间 → 语义是「闲置」而非「登录后硬过期」（PRD A-2）。
- **登出**：`session.clear()` + 显式删除 cookie，然后 302 到 `/items`。
- **cookie 属性**：`HttpOnly=True`（JS 不可读，缓解 XSS 窃取）、`SameSite=Lax`（缓解跨站 CSRF；本系统的写操作全为 POST，Lax 已阻止跨站 POST 自动携带）、`Secure` 仅在 HTTPS 部署时开启，本地 http 演示关闭并在 README 注明。
- **`SECRET_KEY` 管理**：从环境变量读取；缺失时首次启动生成随机值并写入 `instance/secret_key`（已被 `.gitignore` 覆盖）。**严禁硬编码进仓库**——仓库里的密钥等于所有人都能伪造任意 `role=admin` 的会话。
- **角色判定**：`role` 只用于页面可见性与 403 判定，**不作为业务规则的豁免依据**（D-012：管理员同样受 3 件限额约束）。

## 3. 否决的备选方案

### 3.1 备选一：JWT（Bearer token）

**否决理由**：JWT 解决的是「跨域、多客户端共享身份」的问题，而 ADR-001 已把系统限定为同源 SSR，**它唯一的优势在本项目用不上**。代价却全部落在自己身上：① 过期需要 `exp` 校验 + 时钟偏移处理；② 「登出即失效」在没有服务端状态时**同样做不到**（这一点与 cookie session 是同一个限制，JWT 并不能改善，反而常被误解为能改善）；③ 若真要吊销，必须引入黑名单/白名单存储——等于把 session 表重新发明一遍，还多一层签名密钥轮转的运维面。**成本远超收益**（playbook 驳点 2-3）。

### 3.2 备选二：Flask-Session（服务端会话存储）

**方案**：`Flask-Session` 扩展，会话数据存 Redis / 文件系统 / SQLAlchemy 后端，浏览器只持 `session_id`。

**否决理由**：这是**唯一能真正满足「服务端主动吊销」**的方案，但：① 选 Redis 违反 NFR-2（新增外部服务，第二进程）；② 选文件系统后端会引入会话文件的清理任务与并发写问题，且与「单文件库」精神冲突（数据散落两处）；③ 选 SQLAlchemy 后端则等于自建 `sessions` 表（即备选三）再加一层依赖。**在单班 50 人、演示场景下，为「防 cookie 副本」这一低概率风险引入外部依赖，性价比不成立。**

### 3.3 备选三：自建 `sessions` 表 + `session_id` cookie

**方案**：`sessions(id, user_id, created_at, last_seen_at, expires_at)`，cookie 只存随机 `session_id`，每次请求查一次表。

**否决理由（是「暂不采纳」，不是「技术不行」）**：它能在单文件库内实现真正的吊销，且不违反 NFR-2——**这是本 ADR 记录的首选升级路径**。v1 不做，因为：① 每次请求多一次 DB 查询（列表页本就是热点）；② 需要一条过期清理逻辑（启动时或每 N 次请求），多一处可能出错的代码；③ 它解决的威胁（cookie 被复制）在课程演示场景中不在威胁模型内。**若日后要真吊销，从这一条改起，不要改 JWT。**

### 3.4 备选四：把 `user_id` 明文放 cookie（不签名）

**否决理由**：客户端可任意改写，等于人人可改成 `user_id=1` 冒充管理员。零成本越权，无讨论余地。

### 3.5 备选五：服务端全局字典缓存会话（进程内 `dict`）

**否决理由**：单进程下可行，但进程重启即全员登出（演示时重启一次就掉线），且内存无上限。相比签名 cookie 无任何优势，只多一个内存泄漏点。

## 4. 后果

**正面**

- **零外部依赖、零额外查询**：NFR-2 完全满足，会话校验是纯 CPU 的 HMAC 验签。
- 登出、闲置过期两条 FR-1 验收在浏览器行为层面可直接通过测试。
- 代码量最小：无需 token 签发/刷新/校验中间件，无需会话表 CRUD。

**负面 / 明确接受的风险**

- **⚠ 服务端无法主动吊销（本 ADR 的核心代价，人类已裁决接受，D-019）**：登出只清除浏览器那份 cookie；若 cookie 副本已泄露（抓包、共用电脑的历史记录、被复制的浏览器 profile），在 24 小时窗口内仍然有效。**v1 接受此风险**，理由：无状态 session 降低运维成本，与 NFR-2 一致；威胁模型内不存在持有 cookie 副本的攻击者。此风险必须同时写入 `README.md` 的已知限制与 `retrospective.md` 的风险清单，**不得在验收时声称「登出即服务端失效」**。
- **`SECRET_KEY` 是单点**：泄露即全站会话可伪造；轮换即全员登出。写入运维说明。
- **会话内容对用户可见**（签名不加密）：因此只能放不敏感的 `user_id` / `role`；`role` 被用户看到无害（他能看到自己的角色），但**不可把任何「用户不该知道的判断结果」放进 session**。
- **cookie 体积**：每请求携带，故只放三个短字段，不放列表数据。
- **`SameSite=Lax` 不是 CSRF 的完整方案**：它挡住跨站 POST，但同站子域攻击仍可能；本项目单域名部署，接受。若日后加子域，需补 CSRF token。
- **闲置语义依赖 `SESSION_REFRESH_EACH_REQUEST=True`**：若被改成 `False`，语义会静默漂移为「登录后硬过期 24h」，与 PRD A-2 不符——此开关必须显式写在配置里并加注释，不能依赖默认值。

## 5. 下游含义（供阶段 3/4 引用）

- 测试断言「登出后不能用旧 cookie」时，**必须使用浏览器/客户端视角**（删除 cookie 后再请求），不得写成「服务端吊销」的语义，否则测试会造出一个无法实现的承诺。
- 所有受保护路由通过统一的 `login_required` 装饰器拦截；管理路由用 `admin_required`，未登录 302、已登录非管理员 403（FR-1 明确区分这两种情况）。
- `role` 不得参与限额等业务判断（D-012）。
- 会话不存业务数据 → 列表页的限额指示必须每次实时查询（D-013），不能缓存在 session 里。
