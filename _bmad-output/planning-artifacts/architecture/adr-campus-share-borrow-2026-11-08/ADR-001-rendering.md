# ADR-001 · 渲染方式与服务边界

**决定：Flask + Jinja2 服务端渲染，单进程单端口，不设独立 API 层。**

**否决的备选：React 18 + Vite SPA + Flask `/api/*` JSON 接口（前后端分离）。**

## 1. 背景

系统对外只有 5 个页面入口：物品列表（含搜索框，访客可访问）、登录页、我的借阅、借阅/归还的提交动作、管理员物品管理页。业务规模很小：单班、物品 ≤ 50 条（PRD A-1）、单机演示（PRD A-5），全系统唯一的写热点是 `POST /borrow`（PRD §4.3），技术难点集中在一条并发不变量上（NFR-1）。

界面层的实现方式有两条现实路线：把页面交给浏览器端的 React 应用渲染，或交给服务端的模板引擎渲染。AI 架构师初始建议前者，理由是组件化与客户端路由能带来更好的交互表现力，也更贴近当下前端生态的默认形态；该建议作为 draft 提交评审后被否决（D-017）。

**否决的依据不在审美，而在三条硬约束**：① 作业基线 §2 与 PRD §6 均已锁定「严禁前后端分离」「不做独立 API 层」；② NFR-2 要求「一条命令启动」且验收对象是 README 里唯一命令的一次执行，多一条前端构建链就多一个必装工具链与一个失败点；③ 分离后浏览器端无法依赖同源 cookie 会话，会推翻 ADR-003 已定的 Flask session 方案。

## 2. 决定

- **渲染**：Flask + Jinja2 模板，服务端拼装 HTML 后整页返回。模板继承用 `base.html` + `{% block %}`，页面模板与视图函数一一对应。
- **服务边界**：只有一个进程、一个端口；模板、静态资源（CSS/JS/字体）与业务路由由同一进程直接提供。**不设 `/api/*` 层，不返回 JSON 给前端自行渲染。**
- **写操作的响应形态**：一律 `POST` → 处理 → `302` 重定向（PRG 模式），配合 `flash` 传递一次性提示语。所有写操作没有「返回 JSON + 前端跳转」这条路径。
- **错误呈现**：业务失败返回 **真实 HTTP 状态码**（4xx）+ 机器可读错误码（写入响应体或日志供测试断言），同时用同一模板渲染中文提示（PRD §4 错误约定）。状态码不伪装成 200。
- **交互增强的边界**：允许极少量、非必要的原生 JS（如二次确认弹窗 `confirm()`），但**页面数据仍由服务端渲染**；不引入任何框架、不引入 fetch 局部刷新（见否决备选 2）。
- **启动**：`README.md` 声明唯一命令，执行后即可访问（具体命令形态由 ADR-005 定）。

## 3. 否决的备选方案

### 3.1 备选一：React SPA + REST API（主要被否决项）

**方案**：React 18 + Vite 独立单页应用，Flask 只提供 `/api/*` JSON 接口，鉴权用 Bearer token，前端 `npm run build` 产物由静态服务器托管。

**否决理由**：

1. **违反已锁定的技术栈约束** —— 作业基线 §2 写明「严禁前后端分离（React/Vue）」，PRD §6「明确不做」与 §7.2 同样排除。采纳它必须回头改两份已 final 的上游文档，代价与收益不成比例。
2. **直接冲击 NFR-2，且评审人不具备兜底能力** —— 「一条命令启动」会退化为「装 Node → `npm ci` → `npm run build` → 起后端 → 起静态服务」。评审人自述不懂运维，**每多一个环节就多一个现场演示失败的可能**；而 NFR-2 的验收标准恰恰是「命令一次执行即成功」，这条退让没有余地。
3. **连锁推翻会话方案** —— 分离后无法使用同源 cookie，ADR-003 必须从 Flask session 改为 token，凭空多出过期、刷新、吊销三件工作；本项目没有多端复用需求，token 的唯一优势用不上。
4. **重复维护错误码与中文文案** —— PRD 定义 8 个错误码且要求页面渲染中文提示；分离后后端只出码、文案落到前端映射表，两处需同步，属纯粹的新增维护面。
5. **工期** —— 估算净增 1–2 天（脚手架、跨域联调、构建链路排查），占 3 周总工期一成以上，而它不改善 NFR-1 这个真正的评分命门。

### 3.2 备选二：服务端模板 + 前端 fetch 局部刷新（渐进增强）

**方案**：保留 Jinja2 渲染首屏，但借阅/归还按钮改为 `fetch` 提交，前端局部更新列表、不整页刷新。

**否决理由**：为「少刷新一次页面」这一项收益，换来三条成本——① 与 PRG 语义冲突，同一动作要同时支持「表单 POST 302」和「fetch 拿 JSON」两条路径；② 物品状态（可借/在借/停用）需要在模板与 JS 两处各实现一次渲染逻辑，正是 ADR-007 要消灭的「双份真相」；③ 并发冲突后的「列表自动刷新为最新状态」（UJ-4、FR-3）要额外处理。收益与成本严重倒挂，v1 不做。

### 3.3 备选三：Node + EJS 服务端渲染

**方案**：作业基线允许的另一条 SSR 路线，同样单进程单端口。

**否决理由**：技术等价，不构成实质差异；选 Flask 的唯一理由是 Python 生态下 `sqlite3` 为标准库、`werkzeug` 自带密码哈希，`requirements.txt` 可用纯 wheel 装完，对 NFR-2 更友好。Non-decision，记录在此以免下游再问「为什么不是 EJS」。

## 4. 后果

**正面**

- **NFR-2 天然满足**：1 个进程、1 个端口、0 个构建产物、0 个 Node 依赖；冷启动只剩「建表 + 写种子」。
- **会话方案可以最简单**（ADR-003 因此成立）：同源 cookie，无跨域、无 CORS 预检。
- **错误码与文案只有一处真相**：服务层抛业务异常 → 统一错误处理器映射状态码 + 渲染提示。
- 工期比分离方案省 1–2 天，这部分时间直接挪给 NFR-1 的并发测试。

**负面（必须承担的代价）**

- **交互表现朴素**：每次操作整页刷新，无客户端路由的丝滑感；界面美观度本就不优化（PRD SM-C3），此代价被产品目标吸收。
- **前端能力无从展示**：若评分关注前端工程化，本方案不得分——本作业的评分重心是过程可追溯，接受。
- **视图与业务易耦合**：缓解手段是硬性分层——路由函数只做参数收集与异常映射，业务判定全部放在服务层（`services/`），模板只读 `dict`/`Row`，不调用业务函数。此约定将写入阶段 3 的 `project-context.md`。
- **无 API 层可供外部复用**：将来若做小程序，需要新开一层 API；写入「后续扩展」，本期不做（PRD §6.1）。

## 5. 下游含义（供阶段 3/4 引用）

- 所有页面路由返回 `render_template(...)`；不存在「前端页面文件」这一产物。
- 每个写操作必须实现为 `POST` + `302`；测试断言状态码时按 PRD 的 `302 / 409 / 404 / 400 / 403` 编写，不要断言 200。
- 仓库中不得出现 `package.json`、`vite.config.*`、`node_modules`、`dist/`——**这四个文件的存在即为本 ADR 被违反的证据**，可在代码评审时直接检出。
- NFR-2 的验收命令在 ADR-005 中给出，本 ADR 只约束「不得要求 Node 或构建步骤」。
