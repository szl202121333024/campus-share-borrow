# ADR-004 · 密码存储：PBKDF2 不可逆哈希

**决定：使用 `werkzeug.security.generate_password_hash(..., method="pbkdf2:sha256")` 生成不可逆哈希，`check_password_hash` 校验；数据库只存哈希串，绝不存明文。**

**否决的备选：明文存储；MD5 / SHA-1 / 单次 SHA-256（无盐）；自建「SHA-256 + 每用户随机盐」；bcrypt / Argon2。**

## 1. 背景

FR-1 写死两条：密码列存储不可逆哈希；任何页面与日志都不回显密码或哈希。系统的账号来自种子数据（不做注册、不做改密、不做找回），因此「哈希算法变更」几乎不会发生，但**哈希强度决定了数据库泄露时的实际后果**——这是本 ADR 唯一需要权衡的点。

约束：① 密码必须是**不可逆**的，且不是可选项；② 依赖必须能用纯 wheel 装完，不引入需要本地编译的原生扩展（NFR-2「一条命令启动」）；③ 种子数据里的账号密码要能被同一函数验证。

## 2. 决定

- **算法**：PBKDF2-HMAC-SHA256，**显式传 `method="pbkdf2:sha256"`**。
- **盐**：由库自动生成（`salt_length=16`），与算法标识、迭代次数一起编码进哈希串，存单列 `users.password_hash`，格式形如 `pbkdf2:sha256:<iterations>$<salt>$<hash>`。
- **迭代次数**：**不在代码里写死**，沿用 werkzeug 当时的默认值（升级库即自动提高）。硬编码迭代次数会让「升级加密强度」变成一次手改常量。
- **校验**：只允许 `check_password_hash(stored, submitted)`，它内部按哈希串里的参数校验，因此**旧哈希在提升迭代次数后仍然可用**。
- **统一失败**：学号不存在与密码错误返回同一错误码 `INVALID_CREDENTIALS` 与同一句提示（FR-1，防账号枚举）。实现要求：**无论学号是否存在，都执行一次哈希校验**（对不存在的学号校验一个固定的假哈希），避免「查无此人时立即返回」造成的响应时间差。
- **不回显**：`password_hash` 列不出现在任何 `SELECT *` 的模板渲染路径中；ORM/Row 转 dict 时显式白名单字段。
- **种子数据**：种子账号的密码必须在首次建库时用同一函数现场生成，**严禁在源码里写哈希字面量**（写死字面量会让人误以为可以手工构造，且算法默认值一变就失配）。

## 3. 否决的备选方案

### 3.1 备选一：明文存储

**否决理由**：直接违反 FR-1「密码列存储不可逆哈希」。数据库文件会被提交、被拷贝、被演示时投屏；明文意味着任何拿到 `.sqlite` 文件的人都直接获得账号。**无讨论余地——这不是可选项。**

### 3.2 备选二：MD5 / SHA-1 / 单次 SHA-256（无盐）

**否决理由**：这是**快哈希**，设计目标是「算得快」，而密码存储需要的恰恰是「算得慢」。现代 GPU 每秒可计算数十亿次 MD5/SHA-256，8 位以内常见密码在小时级内被穷举；无盐还意味着彩虹表直接命中、相同密码得到相同哈希（一次破解全站复用）。**这是最典型的错误答案**，但在课程项目里出现频率极高，因此明确记录为已否决。

### 3.3 备选三：自建「SHA-256 + 每用户随机盐」

**否决理由**：加盐确实消灭了彩虹表与「相同密码同哈希」，但**没有解决「快」这个根本问题**——攻击者针对单个目标仍需数十亿次/秒的爆破能力。此外自建方案常见的实现错误（盐长度不足、盐与哈希拼接顺序不一致、盐未随哈希一起存、比较时用 `==` 而非恒定时间比较）都会引入新漏洞。**用标准库函数不需要证明自己比它更聪明。**

### 3.4 备选四：bcrypt / Argon2（更强，但本项目不采纳）

**否决理由（诚实版：不否认它更安全，只否认它在本项目的性价比）**：Argon2id 是当下的业界首选，bcrypt 也优于 PBKDF2。否决它们的理由**只有成本**：两者都需要原生扩展（`argon2-cffi` / `bcrypt`），在没有预编译 wheel 的平台上会触发本地编译，直接威胁 NFR-2「一条命令启动」；而 PBKDF2 由标准库 `hashlib` 支撑，`werkzeug` 直接提供，零额外依赖。在「单班演示、威胁模型内无定向攻击者」的前提下，PBKDF2 的抗爆破能力已远超所需。**若日后要升级，升级路径是 bcrypt/Argon2，而不是往回调。**

### 3.5 备选五：把密码或哈希放进会话 cookie

**否决理由**：ADR-003 已定 cookie 只放 `user_id`/`role`/`login_at`；且签名 cookie **不加密**，内容可被客户端读取——放哈希等于把哈希发给每个用户。荒谬但常见，故记录。

## 4. 后果

**正面**

- 数据库泄露不会直接泄露密码；同一密码在不同用户间哈希不同（盐随机）。
- 零额外依赖，NFR-2 不受影响。
- 迭代次数随库升级自动提升，无需迁移代码。

**负面 / 代价**

- **校验是 CPU 密集操作**：PBKDF2 的每次校验要几十万次 HMAC 迭代（数十至上百毫秒）。影响：登录接口变慢（对 50 人规模无感）、**并发测试中若涉及登录需注意串行化影响**。因此登录**不得**放在借阅的写事务内，也不得在列表页反复校验密码。
- **不可逆意味着不可恢复**：忘记密码无法找回（PRD 明确不做找回/改密）。种子账号的密码必须写在 `README.md` 里，否则演示时无人能登录。
- **哈希串长度**：约 100 字节，`password_hash TEXT NOT NULL` 足够，无需定长列。

## 5. ⚠ 待验证项（必须在阶段 4 第一件事核对）

**`generate_password_hash` 的默认算法已经不是 PBKDF2。** Werkzeug 2.3 起把默认 `method` 从 `pbkdf2:sha256` 改为 `scrypt`，因此**不显式传 `method="pbkdf2:sha256"` 就得不到本 ADR 承诺的 PBKDF2**。

- **本机核对状态：未完成。** 本机 `python 3.14.7` 未安装 `werkzeug`（`ModuleNotFoundError`），且本轮网络检索不可用，**无法现场确认默认值**。此条按惯例标 `[ASSUMPTION: werkzeug 默认 method 为 scrypt]`，不作结论使用。
- **阶段 4 的强制核对动作**（三条都要做）：
  1. `inspect.signature(werkzeug.security.generate_password_hash)` 读出实际默认 `method`，并回填本 ADR；
  2. 在代码中**显式**写出 `method="pbkdf2:sha256"`，不依赖默认值；
  3. 写一条测试断言种子账号的哈希串以 `pbkdf2:sha256:` 开头 —— 这样即便将来有人删掉 `method` 参数，测试会立刻失败。
- 若后续决定改用 scrypt（同为不可逆慢哈希、且库默认值），**必须修改本 ADR 与 FR-1 的表述**，不能悄悄漂移：FR-1 只承诺「不可逆哈希」，但本 ADR 承诺的是 PBKDF2，两者需一致。

## 6. 下游含义（供阶段 3/4 引用）

- `project-context.md` 固化为规约：**任何密码写库路径必须经过统一函数，禁止手写哈希、禁止 `hashlib.md5`、禁止在测试里构造明文比较**。
- 测试用例：正确密码 200/302、错误密码 401 `INVALID_CREDENTIALS`、不存在学号 401 `INVALID_CREDENTIALS`（同一响应）、哈希串以 `pbkdf2:sha256:` 开头、任何 HTML 响应体不包含哈希串。
