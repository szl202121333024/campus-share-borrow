# ADR-005 · 并发与部署：SQLite WAL + `busy_timeout` + 单进程

**决定：SQLite 开启 WAL 日志模式与 `busy_timeout`，单进程部署（Flask 内置服务器，`threaded=True`），`README` 声明唯一启动命令 `python app.py`。**

**否决的备选：gunicorn/waitress 多 worker（多进程）；默认 rollback journal；换 PostgreSQL/MySQL；应用层全局锁串行化写。**

## 1. 背景

数据层已锁定为单个 SQLite 文件（PRD NFR-2），而 NFR-1 要求并发写不出错——这两条在 SQLite 上有一个众所周知的摩擦点：**SQLite 同一时刻只允许一个写者**，写者之间靠文件锁协调，锁竞争超时会抛 `database is locked`（`OperationalError`）。

同时 NFR-2 把运维门槛压到极低：一条命令启动、单文件库、无外部服务、启动 < 10 秒、不要求多进程。评审人自述不懂运维（ADR-001 的否决理由之一同样指向这点）。

这两条约束合起来决定了部署形态：**并发正确性必须由数据库自身的机制保证，而不是由「部署成几个进程」保证**；同时部署形态越简单，NFR-2 越稳。ADR-002 已经把两条不变量分别交给了部分唯一索引与 `BEGIN IMMEDIATE`，本 ADR 只解决「这些机制在什么运行配置下可靠」。

## 2. 决定

### 2.1 数据库 PRAGMA（每次建立连接时设置，且写进启动自举）

| PRAGMA | 值 | 作用 | 生效范围 |
|---|---|---|---|
| `journal_mode` | `WAL` | **读不阻塞写**：列表页查询与借阅写入可并行，大幅减少 `SQLITE_BUSY` | 持久化在库文件中，设一次即可（仍每次启动都设，幂等） |
| `busy_timeout` | `5000`（ms） | 拿不到锁时**等待而非立即报错**，让排队在 ADR-002 的写事务内自然完成 | **每连接**，必须每次建立连接时设置 |
| `foreign_keys` | `ON` | 启用外键约束（ADR-002 依赖它做「删除有在借记录直接报错」） | **每连接**，SQLite 默认关闭 |
| `synchronous` | `NORMAL` | WAL 下的常规取舍：崩溃安全性足够，写入不必每次 fsync | 每连接 |

> **易错点**：`journal_mode` 是库级持久设置，`busy_timeout`/`foreign_keys`/`synchronous` 是**连接级**设置。后者若只在「第一次建库时」设置一次，之后每个新连接都会退回默认值（`busy_timeout=0`、外键关闭），**并发与级联删除会静默失效**。因此统一在一个「开连接」函数里集中设置，全项目不允许绕过它直接 `sqlite3.connect()`。

### 2.2 连接管理

- **每请求一个连接**：存于 `flask.g`，在 `teardown_appcontext` 中关闭。不使用跨请求的全局连接（全局连接在 `threaded=True` 下会被多线程共享，SQLite 连接非线程安全，是隐蔽的崩溃源）。
- **写事务显式开启**：业务写路径统一 `BEGIN IMMEDIATE`（ADR-002），连接需 `isolation_level=None`（自动提交模式）以便精确控制事务边界，**不使用 Python `sqlite3` 模块的隐式事务**（它在 DML 前自动 `BEGIN`，且是 `DEFERRED`，违反 NFR-1 的禁令）。
- **行工厂**：`row_factory = sqlite3.Row`，模板与业务层按字段名取值，避免位置索引错误。

### 2.3 部署形态

- **单进程**：`python app.py`，内部 `app.run(threaded=True)`。线程模型足以处理「两个并发借阅请求」——并发性来自线程，写互斥来自数据库锁，二者不冲突。
- **一条命令**：`python app.py`：自动建表（若库文件不存在）、写入种子数据（≥2 学生 + 1 管理员 + ≥6 物品）、启动服务、打印访问地址。无需迁移脚本、无需第二个进程、无需 Node（ADR-001）。
- **依赖声明**：`requirements.txt` 固定小版本（如 `Flask==3.1.*`），`pip install -r requirements.txt` 作为唯一前置步骤，写进 README。
- **失败可诊断**（NFR-2）：端口占用、数据库不可写时，打印一行中文原因并以非零码退出，不静默挂起。
- **日志**：写路径打印 `item_id`/`user_id`/耗时；**严禁打印密码、哈希、完整 cookie**（ADR-004）。

## 3. 否决的备选方案

### 3.1 备选一：gunicorn / waitress 多 worker（多进程）

**否决理由**：这不是「不能跑」，而是**收益用不上、风险立刻出现**。① 多进程各有独立连接池，SQLite 写锁跨进程协调，锁等待时间随 worker 数增长，`database is locked` 的概率反而上升；② 需要进程管理配置（worker 数、超时、重启策略），NFR-2 的「一条命令」变成「先起一个 supervisor」；③ 本项目最坏并发是「两个人同时点借阅」，单进程多线程绰绰有余，横向扩容没有场景。**用并发正确性换吞吐，在 50 条物品规模上是纯亏损。**

### 3.2 备选二：默认 rollback journal（不启 WAL）

**否决理由**：rollback journal 下**读与写互斥**——列表页查询会阻塞借阅写入，反之亦然。在「借阅成功后 302 回列表页」这个高频动作里，读写交替会让 `SQLITE_BUSY` 显著增多，而 WAL 让读者看到事务开始前的快照、不与写者争锁。代价仅是库目录多出 `-wal` 与 `-shm` 两个文件（须写入 `.gitignore`）。**成本几乎为零，收益直接命中 NFR-1。**

### 3.3 备选三：换 PostgreSQL / MySQL

**否决理由**：与 NFR-2 的「单文件库、无外部服务、一条命令启动」正面冲突——多一个服务要装、要起、要配账号。本项目没有需要关系型数据库高级能力（多写者高并发、复杂事务隔离级别）的场景。

### 3.4 备选四：应用层全局锁（`threading.Lock`）串行化所有写

**否决理由**：与 ADR-002 的 §3.2 同源——把正确性寄托在「部署形态永远是单进程」上；一旦有人按备选一改成多 worker，锁在进程间不共享，保护立刻消失且**没有任何报错**。唯一索引 + `BEGIN IMMEDIATE` 是数据库级保证，不依赖部署形态，因此更可靠。此外全局锁会把不相关的写操作（管理员新增物品）也串行化，粒度过粗。

### 3.5 备选五：SQLAlchemy 等 ORM 管理事务

**否决理由**：ORM 的隐式事务与 `BEGIN DEFERRED` 语义，与本项目「必须 `BEGIN IMMEDIATE`、禁止延迟事务」的硬禁令（NFR-1）冲突；要在 ORM 里精确控制需要大量配置与版本相关行为，调试成本高于收益。50 条规模、6 个用例的系统，**显式 SQL 更短、更可审计**（评审人要能一眼看出没有「先查后写」）。此否决与 ADR-001「不多一层抽象」一致（PRD SM-C2：不优化代码层数）。

## 4. 后果

**正面**

- 读写并行，列表页与借阅互不阻塞，`SQLITE_BUSY` 概率显著下降。
- `busy_timeout=5000` 让锁竞争表现为「短暂排队」而非「用户看到 500」。
- 部署最简单：一个进程、一条命令、一个文件，NFR-2 的三条验收（一条命令、单文件、<10s）同时满足。

**负面 / 代价**

- **写吞吐上限 ≈ 数百次/秒**（SQLite 单写者）。规模内无问题，但需明确：**写事务内只做数据库操作**——不得在事务里渲染模板、调哈希函数（ADR-004 的登录哈希是几十毫秒级）、发网络请求，否则持锁时间被拉长，其他写者会排队到 `busy_timeout` 超时。
- **`busy_timeout` 超时后的处理**：仍可能抛 `OperationalError: database is locked`。映射为 **503 + 可读提示**，而非 500 或静默重试；并发测试里若出现此错误，应视为「事务过长」的信号而不是加长超时。
- **WAL 的运维副作用**：`-wal`/`-shm` 文件需加入 `.gitignore`；**备份/复制必须连同 `-wal`**，否则会丢最近的事务；`-wal` 在长时间读取未结束时不会自动 checkpoint（演示场景不会触发）。
- **单进程 = 单点**：进程崩溃即服务中断，无自动重启。演示场景接受，写入 README 的已知限制。
- **`threaded=True` 的并发上限**：线程数无上限但受 GIL 限制；本项目并发场景是「2 个请求」，无影响。
- **`synchronous=NORMAL`**：极端断电可能丢失最后一个事务（不损坏库）。课程演示可接受。

## 5. ⚠ 待验证项

- **运行时版本兼容性**：本机为 `python 3.14.7`（`sqlite3 3.50.4` ✓ 支持部分索引与 WAL）。但 **Python 3.14 较新，Flask / Werkzeug 的官方支持矩阵未在本轮核实**（本机未装 Flask，网络检索不可用）。阶段 4 第一步须验证 `pip install -r requirements.txt` 在 3.14 下无编译/兼容问题；若不通过，**退回到 3.12 并在 README 声明版本**，不要现场 patch 依赖。标 `[ASSUMPTION: Flask 3.1 在 Python 3.14 可运行]`。
- **冷启动 < 10s**：需实测（含建表 + 种子 + PBKDF2 生成 3 个账号哈希——注意 PBKDF2 每个哈希数十毫秒，属可接受范围）。此数值同时是实验 A 的「事后验证」列证据。
- **WAL 是否真的生效**：启动自举后应断言 `PRAGMA journal_mode` 返回 `wal`（而不是 `delete`），否则说明设置未落盘（常见原因：在有活动事务时切换 journal_mode 会失败且静默返回原模式）。

## 6. 下游含义（供阶段 3/4 引用）

- `project-context.md` 固化：① 所有连接必须经统一 `get_db()`；② PRAGMA 四项在 `get_db()` 内集中设置；③ 写路径 `BEGIN IMMEDIATE`，禁用 `BEGIN DEFERRED` 与隐式事务；④ 事务内禁止耗时操作。
- NFR-1 的并发测试（20 轮）必须在**单进程 `threaded=True`** 的真实部署下跑，不能用「两个串行请求」冒充。
- `README.md` 必须写明：唯一启动命令、前置 `pip install -r requirements.txt`、种子账号密码、已知限制（单进程、无自动重启、无会话吊销）。
