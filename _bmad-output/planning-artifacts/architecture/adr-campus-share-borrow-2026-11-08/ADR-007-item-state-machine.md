# ADR-007 · 物品状态机：「存储态 + 派生态」混合模型

**决定：`items.status` 只存 `available` / `unavailable` 两个值，唯一写入者是管理员；「在借」`borrowed` 不存储，由「该物品是否存在未归还借阅记录」派生。展示优先级 `unavailable` > `borrowed` > `available`。**

**否决的备选：三态存储（`available`/`borrowed`/`unavailable`）；纯派生（不存状态列）；数据库触发器同步 `borrowed` 列；归还时顺手改 `items.status`；用 `loans.is_returned` 布尔标志代替 `returned_at`。**

## 1. 背景

一件物品在业务上会同时受**两种互相独立的事实**影响：

1. **管理员的管理意图** —— 这件东西当前是否对外提供（下架维修 = 不提供）；
2. **借阅的现实** —— 这件东西此刻是否在某人手上。

这两个事实**可以同时成立**：一台投影仪正在被借走，同时管理员决定它坏了、下架维修。若状态机只有一个三值列，就必须回答一个无解的问题——「停用中又在借，该显示哪个？归还后要不要自动回弹成可借？」（这正是 D-005 反复讨论的隐患）。

更麻烦的是**写入路径**：如果「在借」也是存储值，那么借阅要写 `loans` + `items` 两处，归还也要写两处，删除还要写两处。每一次双写都是一个潜在的不一致窗口，而 NFR-1.4 要求「任何并发场景结束后不存在『有在借记录但物品显示可借』」——**用双写去满足这条要求，等于用代码纪律去对抗结构缺陷**。

D-014 已经确定两条硬规则：归还逻辑只写 `loans`、禁止更新 `items.status`；物品状态的唯一修改入口是管理员。本 ADR 把这两条规则落成一个具体的数据模型（D-015）。

## 2. 决定

### 2.1 状态定义

| 层 | 取值 | 谁是唯一写入者 | 物理保障 |
|---|---|---|---|
| **存储态** | `available`（可借）、`unavailable`（停用） | **仅管理员**（停用 / 恢复上架） | `CHECK (status IN ('available','unavailable'))`，见 ADR-002 |
| **派生态** | `borrowed`（在借） | **无人写入**，由查询算出 | `EXISTS (SELECT 1 FROM loans WHERE item_id = items.id AND returned_at IS NULL)` |

- **展示优先级**：`unavailable` > `borrowed` > `available`。即停用优先于在借——管理员说下架就是下架，学生端不展示，但借阅者的记录照常保留、照常可归还。
- **`borrowed` 永远不是存储值**：`items.status` 的任何写入路径出现 `'borrowed'` 字面量都是 bug，且会被 `CHECK` 约束直接拒绝（物理层的第二道防线）。

### 2.2 派生规则集中在一处

- 全项目**只允许一个**「物品 + 在借状态」的组合查询实现（`list_items_with_state(...)`），所有列表页、搜索页、管理页复用它。
- 展示优先级比较（`unavailable` > `borrowed` > `available`）只允许一个函数实现，模板只做渲染。
- **理由与 D-013 同源**：不变量最大的敌人不是并发，而是「同一规则被写了两遍，然后只改了一处」。两处 JOIN 写法会让「在借」有两个定义。

### 2.3 与归还的关系（D-005 的落地）

- 归还**只写 `loans.returned_at`**，不碰 `items`（D-014，可静态检查：归还路径的 SQL 中不得出现 `UPDATE items`）。
- 因此「停用物品被归还后仍为 `unavailable`」**自动成立**，不需要任何 `if` 判断——因为归还根本没能力改它。
- 「未停用的物品归还后回到可借」也自动成立——因为派生查询不再找到未归还记录，`borrowed` 消失。
- 这两个行为**出自同一个结构事实**，而不是两条分头维护的业务规则。FR-4 要求 A/B 两个独立用例，正是为了证明「状态没被归还逻辑偷偷改写」。

## 3. 否决的备选方案

### 3.1 备选一：三态存储（`available` / `borrowed` / `unavailable`，初始建议）

**否决理由**：

1. **归还必须双写** —— 关记录 + 改物品状态两条语句，落在同一事务里虽可保原子，但**「停用中的物品归还后该不该回弹」变成了一处需要显式分支的写**（D-005 的隐患正来自这里）；双写路径越多，漏写一处就是静默的脏状态。
2. **产生不一致窗口，直接威胁 NFR-1.4** —— `borrowed` 是「未归还记录存在」的**冗余副本**，任何一次漏写、手工改库、异常中断，都会造成「有在借记录但显示可借」。而要求「不存在中间态」的最佳方式，是**让中间态在结构上无法存在**。
3. **破坏单写入者约束** —— 状态列出现两个写入者（管理员 + 借阅/归还流程），D-014 的「归还只写 loans」就无法通过代码检查证明。

### 3.2 备选二：纯派生（连 `unavailable` 也不存，全部从借阅记录推）

**否决理由**：「停用」不是一次借阅事件，它无法从 `loans` 派生。要做到纯派生，必须再建一张 `item_availability_events` 之类的表来承载管理动作，本质是把状态列换了个地方存，还多了一次聚合。**没有收益，只有抽象税。**

### 3.3 备选三：数据库触发器同步 `items.borrowed` 列

**方案**：`loans` 上的 `AFTER INSERT / AFTER UPDATE` 触发器自动维护 `items.status`。

**否决理由**：把业务规则藏进 schema 的反面案例——① 触发器里的判断无法被单元测试直接观测，出错时的报错也很难映射成 PRD 要求的 409/400 语义；② 与 ADR-005「显式 SQL、可审计」的原则冲突（评审人要能一眼看出没有「先查后写」）；③ 它保留了「第二份真相」，只是把维护责任从应用层挪到了数据库层，不一致的**可能性**依然存在。

### 3.4 备选四：归还时顺手 `UPDATE items.status = 'available'`（最直觉的写法）

**否决理由**：这正是 D-014 明令禁止的写法，也是 D-005 争了半天的那个坑。它会直接导致「停用物品归还后自动上架」——管理员下架的坏投影仪，被人还回来就重新出现在学生列表里，安全与流程双重错误。**用派生模型后，这条错误写法在结构上不成立**（因为归还只写 loans）。

### 3.5 备选五：用 `loans.is_returned` 布尔标志代替 `returned_at` 时间戳

**否决理由**：① FR-4 要求「写入归还时间」，布尔值没有时间信息，逾期判断与展示都会缺数据；② 部分唯一索引的条件 `WHERE returned_at IS NULL` 若改为 `WHERE is_returned = 0`，语义等价但丢失了「何时归还」这一事实；③ 时间戳天然可判空、可排序、可算逾期天数，一个字段承担三件事，布尔只能承担一件。

## 4. 后果

**正面**

- **NFR-1.4「无中间态」由结构保证**，而不是由代码纪律保证：不存在「物品状态」与「借阅记录」两份数据，也就没有不一致的可能。
- **D-014 可静态检查**：归还路径的 SQL 里没有 `UPDATE items`，`grep` 即可验收。
- **D-005 的两个用例自动成立**：停用物品归还后保持 `unavailable`、恢复上架后变 `available`——一个是「归还改不到它」，一个是「管理员改得动它」。
- **管理动作无死角**：停用与在借是两个独立事实，可以并存，不会出现「既不能删也不能下架」的死胡同（SM-4）。
- 派生态可直接用于列表渲染，无需缓存失效逻辑。

**负面 / 代价**

- **每次列表查询都要关联借阅表**（`LEFT JOIN` 或 `EXISTS`）。50 条规模下开销可忽略，但必须**一次查询取全量**，禁止对每条物品单独查在借人（N+1）。在借人姓名需与 `users` 再关联一次，仍在同一条 SQL 内完成。
- **派生逻辑写错会静默出错**：漏写 `AND returned_at IS NULL` 会让已归还的物品永远显示「在借」。此类错误不会有任何异常，只能靠测试发现——因此必须有「借出 / 停用 / 归还 / 恢复」四态组合的单测与列表渲染断言。
- **管理员列表页的 SQL 更复杂**：要同时看到停用与在借，需要 `CASE` 组合出展示态，并区分「停用」与「停用 + 在借」。这是本模型唯一明显变复杂的地方。
- **`items.status` 的 `CHECK` 约束与 ADR-002 强耦合**：若有人为了"顺手"把 `borrowed` 加进枚举，必须同时改 ADR-002 的 schema——这是一次有意识的架构变更，不是一次临时改动。

## 5. 下游含义（供阶段 3/4 引用）

- `items` 表的 `status` 取值集合被 `CHECK` 锁死为两值；任何 `'borrowed'` 字面量出现在 `items` 写入路径即为违反本 ADR（D-015）。
- 归还路径禁止 `UPDATE items`（D-014）；代码评审时 `grep -n "UPDATE items" services/` 应仅出现在管理员停用/恢复上架两处。
- 列表页与 `/my-loans` 的状态展示**必须**来自同一个派生函数，禁止第二份 SQL（同 D-013 精神）。
- 阶段 3 必须包含的验收标准（本条已被升格为独立断言）：
  - 借出 → 停用 → 归还：`loans.returned_at` 非空 **且** `items.status = 'unavailable'`；
  - 恢复上架：`items.status = 'available'` 且重新出现在学生列表；
  - 两用例**不得合并**（FR-4 明确要求）。
- NFR-1.4 的交叉验证方式：并发场景结束后，列表页渲染出的状态与 `loans` 表的未归还计数必须一致（`borrowed` ⇔ `COUNT = 1`）。
