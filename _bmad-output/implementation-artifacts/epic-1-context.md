# Epic 1 Context: 认证与浏览 —— 先让人看得见，再让人被认出

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

让评审人在干净机器上用一条命令启动一个自带演示数据的系统；访客无需登录即可浏览和搜索物品，学生与管理员则通过同一个学号登录入口建立可信身份。这个史诗先提供可复现的运行环境、开放的只读浏览和明确的访问边界，为后续借还与物品管理提供统一基础。

## Stories

- Story 1.1: 一条命令启动、自动建表与种子数据
- Story 1.2: 学号登录、登出与会话访问控制
- Story 1.3: 物品列表与关键字搜索

## Requirements & Constraints

- 首次启动必须自动建表并预置至少两个学生、一个管理员和六件覆盖图书与器材的物品；全部业务数据只存入一个 SQLite 文件，冷启动不超过 10 秒。数据库不可写或端口被占用时，必须打印一行可读原因并以非零状态退出。
- 不提供注册、改密、找回密码、第三方登录、登录失败锁定或验证码。学生与管理员共用登录入口，以学号和密码认证。
- 登录成功后建立会话并返回原目标页；没有目标页时进入物品列表。重复访问登录页不再展示表单。登出通过 POST 完成并清除浏览器会话。
- 会话闲置超过 24 小时后失效；失效后访问受保护页面时跳回登录页并提示过期。未登录访问受保护页面或写操作时，也必须携带原目标路径跳转登录。
- 浏览与搜索对访客开放，登录门槛只落在受保护页面和写操作上。学生访问管理员区域必须得到真实 403，不得误当作未登录重定向。
- 密码只能以不可逆哈希保存；学号不存在和密码错误必须返回相同状态、错误码与中文提示，避免账号枚举。任何页面或日志均不得泄露密码、哈希或完整会话 cookie。
- 物品列表只显示非停用物品，先图书后器材、组内按名称升序。搜索按名称包含匹配，忽略英文大小写和首尾空白；通配符按普通字符处理，无匹配仍是 200 空状态。
- 列表展示名称、类别、状态和在借时的应还日期。访客不得看到借阅人姓名，登录用户可以看到；学号不出现在任何列表或响应中。列表禁止跨用户缓存。
- 业务失败必须返回真实 4xx、机器可读错误码及中文提示，禁止以 200 携带错误文案。

## Technical Decisions

- 使用 Flask + Jinja2 服务端渲染，单进程、单端口，不设独立 API 层，也不引入前端构建链。写操作统一采用 POST + 302 的 PRG 模式，一次性提示通过 flash 传递。
- 数据库连接按请求创建并集中配置 WAL、忙等待、外键和同步级别；连接不得跨请求共享。所有连接只能走统一入口，启动时必须主动确认 WAL 已生效。
- 使用 Flask 签名 cookie session，服务端不保存会话。会话只包含用户标识、角色和登录时间，永久会话有效期为 24 小时，并在每次请求时刷新，以保持“闲置过期”语义。
- cookie 必须 HttpOnly、SameSite=Lax；Secure 仅在 HTTPS 部署时开启。签名不提供加密，因此会话中不得放密码、哈希或业务数据。
- 会话密钥从环境变量读取；缺失时生成随机值并存入被忽略的实例密钥文件，严禁把密钥硬编码进仓库。
- 无状态 cookie 无法由服务端主动吊销，这是已接受的限制：登出只保证浏览器清除 cookie，不能承诺被复制的旧 cookie 立即失效。若未来需要真吊销，优先升级为单文件库中的服务端会话表，而不是 JWT。
- 密码使用 Werkzeug 的 PBKDF2-HMAC-SHA256，并显式指定算法，不能依赖库默认值。登录校验必须统一经过安全函数；学号不存在时也对固定假哈希执行一次校验，避免明显时序差。
- 登录密码校验属于耗时操作，不得放入数据库写事务。路由只收集参数和映射结果，业务判定放在服务层，模板只负责展示。
- 未登录拦截与管理员授权分别由统一守卫完成；角色只用于访问控制，不得成为后续借阅限额的豁免条件。

## UX & Interaction Patterns

- 首页即物品列表，访客可以直接看到可借状态，再决定是否登录。登录页只提供学号与密码两个字段，不为管理员另设入口。
- 页面只需保证信息可读、状态可见，不追求独立设计系统。登录失败在原表单显示统一提示；业务错误使用统一错误模板。
- 非管理员不展示后台入口。物品操作带来的状态变化通过整页重定向呈现，不引入 fetch 局部刷新或第二套前端状态。

## Cross-Story Dependencies

- Story 1.1 提供数据库结构、种子账号与物品，是 Story 1.2 和 Story 1.3 的前置条件。
- Story 1.2 提供登录态和统一访问守卫；Story 1.3 用它区分访客与登录用户的展示差异，后续借阅、归还和管理故事也复用这些守卫。
- Story 1.3 提供学生端列表与派生状态展示。登录后的限额指示由后续专门故事补齐，避免浏览故事反向依赖借阅额度实现。
